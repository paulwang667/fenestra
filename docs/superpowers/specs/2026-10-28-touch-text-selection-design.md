# 移动端文本选择、编辑菜单与剪贴板 设计

## 为什么做

Android 和 iOS 都已经能跑 fenestra 应用了，但在手机上，"选中文字、复制、粘贴"这件最基本的事还做不了：

- **触摸下没有选择交互**。fenestra 的文本选择是照鼠标设计的：拖动选择、双击选词、Cmd/Ctrl+C 复制。手机上没有键盘快捷键，拖动手指是滚动，长按被翻译成右键。结果是只读文本没法选，输入框里也没有选择手柄、放大镜和编辑菜单。
- **手机上没有系统剪贴板**。`fenestra-shell` 里的剪贴板桥接（`OsClipboard`）用的是 arboard，它不支持 Android 和 iOS。Android 构建把它排除了，退回内存剪贴板；iOS 情况相同，复制的内容出不了应用，别的应用复制的内容也粘贴不进来。

用户（2026-10-28）要求两种用法都支持：

1. **消息气泡**：长按弹出应用自己的菜单（复制整条、转发、引用……），其中的"选择文本"进入选择状态。在选择状态下拖动手柄只选一段，再从编辑菜单复制。
2. **输入框**：系统那一套，长按、放大镜、手柄、剪切/复制/粘贴/全选。

用户对外观和行为的要求是：**和其他主流移动开发框架保持一致的用户体验**。Flutter、原生 Android、原生 iOS 都是按平台各自适配的，这里也照此做。

## 目标

1. 触摸设备上，只读的可选文本（`.selectable()`）和输入框都能用手指选择文字：长按选词，拖动两端的选择手柄调整范围。
2. 拖动手柄或在输入框里长按移动光标时，手指上方出现放大镜。
3. 有选区时，或在输入框里点光标时，出现编辑菜单，菜单项按情况给出：
   - 只读文本：复制、全选；
   - 输入框：剪切、复制、粘贴、全选（选区为空时只有粘贴和全选；剪贴板为空时没有粘贴；密码框没有剪切和复制）。
4. 手柄、放大镜和编辑菜单的外观和行为按平台适配：Android 用 Material，iOS 用 UIKit 风格（见下文"平台风格"）。
5. Android 和 iOS 上，复制和粘贴走系统剪贴板，和其它应用互通。
6. 应用可以在代码里让某段可选文本进入选择状态（全选并显示手柄和菜单）。wechat-ui 的"选择文本"菜单项就靠这个实现。
7. wechat-ui 接上：给消息气泡新做一个长按菜单（见第 5 部分）。

## 不做什么

- 不调用系统原生的编辑菜单（iOS 的 `UIEditMenuInteraction`、Android 的 `ActionMode` 浮动工具条）。菜单由 fenestra 自己绘制，样式模仿平台。
- 菜单里不放"查询""翻译""分享""自动填充"等系统扩展项。
- 剪贴板只处理纯文本，不处理图片、富文本和 HTML。
- 不做跨多个元素的选择。和现在一样，同一时刻只有一段选区（像浏览器那样）。
- 不做文字拖放。
- 不改桌面和网页：鼠标拖选、双击和三击、右键菜单、快捷键都保持原样。所有新行为只在**触摸**输入时启用。
- 不验证 iPad 指针、外接鼠标和触控板。

## 绝不能出现的情况

- **滚动被抢**。不在选择状态时，在文字上拖动手指仍然是滚动，包括输入框里的多行文本。
- **应用的长按菜单被抢**。元素（或它的祖先）自己处理右键（`on_right_click` / `on_right_click_at`，触摸下长按就是右键）时，长按交给应用，不去选词。wechat-ui 的消息气泡加上菜单后就属于这种情况。
- **输入法状态错乱**。在输入框里用手柄改选区、剪切或粘贴之后，Android GameActivity 和 iOS 的输入法镜像都必须同步到新的文本和选区。已有的 `ImeSync` 负责推送，不能出现输入法拿着旧文本继续组字的情况。
- 桌面行为有任何变化（现有测试和截图对比都必须照旧通过）。

## 现状（实现时依赖的事实）

- **触摸翻译**在 `fenestra-shell/src/touch.rs`。手指驱动指针；拖动超过 `TAP_SLOP`（10 逻辑像素）就变成滚动（`InputEvent::Pan`），除非 `fenestra_core::owns_touch_drag` 判定这次按下属于某个元素：带拖动处理的元素、滑动手势、拖放源，或者文本输入框（目前在输入框里拖动是选择文字）。手指静止 `LONG_PRESS`（0.5 秒）就发一次右键（`RightDown`/`RightUp`），松手不再点击。
- **只读文本选择**：`Element::selectable()`；选区存在 `FrameState::static_sel`（元素、parley 选区、是否正在拖动），同一时刻只有一段。
- **输入框**用 parley 的编辑器，选区通过 `FrameState::ime_text_state` 和 `InputEvent::ImeState` 与输入法同步。
- **剪贴板接口**是 `fenestra_core::Clipboard`（`get`/`set` 文本，`get_image`/`set_image` 图片，图片默认不支持），通过 `FrameState::set_clipboard` 注入。桌面用 `OsClipboard`（arboard），网页用 `WebClipboard`，无头测试用 `MemoryClipboard`。
- **触感**：`Haptic::LongPress` 由 `touch_haptic` 在长按产生了应用消息时触发。
- **`unsafe` 规则**：工作区 `unsafe_code = "deny"`，只有 `fenestra-raster/src/coretext.rs` 一个模块允许使用（用户 2026-10-28 批准，用于 iOS emoji）。本设计再加一个例外，见第 4 部分。
- **wechat-ui 的消息**：消息正文已经是 `.selectable()`（`native/src/ui.rs` 的 `message_bubble`、`text_bubble`、`code_card`）。气泡**还没有**长按或右键菜单；整个应用里只有会话列表的行（`chat_row`）有 `on_right_click` 和 `context_menu`。

## 怎么做

### 1. 触摸选择交互（fenestra-core）

core 需要知道一次指针输入来自触摸，才能只对触摸切换到移动端行为。**我的决定**：shell 在把触摸翻译成指针事件时，告诉 core 当前输入来自触摸（具体用新的 `InputEvent`、指针事件上的字段，还是 `FrameState` 上的状态，由实现者决定），鼠标输入时清除这个标记。

只在触摸输入下生效的行为：

- **长按**：落点的命中链上（落点元素及其所有祖先）只要有元素处理右键（`on_right_click` / `on_right_click_at`），就照旧发右键，交给应用。否则，落点是可选文本或输入框时，选中落点所在的词，显示手柄和编辑菜单，并触发 `Haptic::LongPress`。**我的决定**：祖先上的应用菜单优先，和原生平台一致（iOS 列表单元格长按出上下文菜单，不选里面的文字）。代价是带右键菜单的行里的可选文字无法用长按直接选择，要靠应用提供"选择文本"入口（第 3 部分）。不新增 `on_long_press` API。
- **输入框里长按后不松手拖动**：移动光标并显示放大镜（iOS 惯例）。
- **双击**输入框里的文字：选词，同上。
- **单击**：
  - 输入框里单击一次，移动光标，和现在一样。
  - 再点一次光标本身，弹出编辑菜单。没有选区时菜单项是"粘贴、全选"，iOS 上光标所在位置的菜单也是这样。
  - 点选区以外的地方，取消选择，手柄和菜单消失。
- **拖动手柄**：手柄拥有这次触摸，不滚动。选区端点跟着手指移动，按字形边界吸附（复用 parley 的 hit test），两个手柄可以互相越过（起止交换）。拖到滚动容器边缘时自动滚动。拖动时编辑菜单隐藏，松手后重新出现。
- **触摸下在输入框里直接拖动**：改为滚动或什么都不做，不再选择文字。拖动选择改由手柄完成，和主流移动端一致。`owns_touch_drag` 在触摸下对输入框返回"不拥有"，手柄除外。
- 选区所在的元素滚出视野时，手柄和菜单跟着隐藏，滚回来再出现。

### 2. 手柄、放大镜、编辑菜单（绘制）

三者都画在覆盖层上（和现有的浮层一样位于内容之上，并遵守安全区），用 fenestra 自己的绘制路径，raster 和 vello 都要支持。

**平台风格**（**我的决定**：参照 Flutter 的 `MaterialTextSelectionControls` 和 `CupertinoTextSelectionControls`）：

| | Android（Material） | iOS（Cupertino） |
|---|---|---|
| 手柄 | 水滴形，挂在选区两端的下方，颜色取主题强调色 | 竖线加圆点：起点的圆点在上，终点的在下，颜色取强调色 |
| 放大镜 | 圆角矩形，约 1.25 倍 | 胶囊形，约 1.25 倍 |
| 编辑菜单 | 浮动工具条：圆角卡片、阴影、文字按钮横排 | 深色圆角横条，按钮之间有分隔线 |
| 菜单位置 | 选区上方，空间不够时放下方，水平方向夹在屏幕内 | 同左 |

- 风格默认按编译目标选（`target_os = "android"` 用 Material，`"ios"` 用 Cupertino，其他平台用 Material）。测试和应用可以覆盖（具体放在 `Theme` 还是 `FrameState` 由实现者决定），让无头测试在 macOS 上也能截两种风格的图。
- **菜单文字**按 `Fonts::set_locale` 设置的语言显示：中文是"剪切 / 复制 / 粘贴 / 全选"，其它语言是 "Cut / Copy / Paste / Select All"。**我的决定**：fenestra 目前没有通用的本地化机制，第一版只内置这两种语言。
- **放大镜**要把手指下方那块内容放大后重画一遍，而不是从 GPU 读回像素。两个后端都按这个路数做（同一块内容在缩放变换和裁剪下再画一次）。
- 触摸目标的大小遵守平台最小尺寸：手柄的可触区域至少 44×44 逻辑像素。

### 3. 程序化进入选择

应用要能让一段 `.selectable()` 文本全选，并显示手柄和菜单。wechat-ui 用它实现消息气泡长按菜单里的"选择文本"。接口形式（命令、元素上的标记，还是 `FrameState` 方法）由实现者按 fenestra 现有的 `Cmd` 和 focus 惯例决定，需要满足：

- 指定目标元素的方式和 fenestra 现有的按 id 或 label 找元素的方式一致；
- 目标不存在或不可选时，什么都不发生（不 panic）；
- 无头测试里可以触发并断言（选区范围、菜单出现）。

### 4. 系统剪贴板（fenestra-shell）

- **Android**：通过 JNI 调用 `ClipboardManager`（`getPrimaryClip`/`setPrimaryClip`，纯文本 `ClipData.newPlainText`）。JavaVM 和 Context 从 winit 暴露的 `AndroidApp` 取。
- **iOS**：通过 `UIPasteboard.generalPasteboard` 的 `string` 属性读写。
- 两者都实现 `fenestra_core::Clipboard` 的 `get`/`set`；图片沿用默认（不支持）。Android 和 iOS 上的窗口运行器默认注入各自的实现，取代现在的内存剪贴板。
- 读取失败（权限、异常）时返回 `None`，写入失败时静默。Android 10 起只有获得焦点的应用能读剪贴板，正常情况下满足。
- iOS 14 起读剪贴板时系统会显示"已从某应用粘贴"的提示。所以**只在用户点"粘贴"时读**，不要为了决定是否显示"粘贴"项而读剪贴板。判断剪贴板有没有内容用 `hasStrings`（不会触发提示）；Android 上用 `hasPrimaryClip`。这意味着 `Clipboard` 接口需要新增一个"有没有文本"的查询，并给出默认实现（默认用 `get().is_some()`）。

**`unsafe`**：这两种实现都必须用 `unsafe`（JNI 从原始指针构造 JavaVM，以及 objc2 调用）。用户 2026-10-28 决定**扩大例外**：fenestra-shell 的移动端剪贴板模块（Android 和 iOS 的实现放在这一个模块里，或者它下面的两个子模块）也允许 `unsafe`，和 `coretext.rs` 一样用模块级 `#![allow(unsafe_code)]`。工作区 `Cargo.toml` 里关于 `unsafe` 的注释和 CHANGELOG 要同步更新，写明例外现在有两处。这样所有 fenestra 移动应用默认就能用系统剪贴板，不需要应用自己写代码。

### 5. wechat-ui：消息菜单（新功能）

气泡目前没有菜单，这里新做一个，仿照会话列表行已有的做法（`on_right_click` 加 kit 的 `context_menu`，由应用状态控制是否显示）。用户 2026-10-28 决定的内容：

- **触发**：触摸长按气泡（会触发 `Haptic::LongPress`），桌面上**右键气泡也打开同一个菜单**。桌面上在气泡里拖动鼠标选择文字的行为不变。
- **范围**：文字消息和代码卡片都有这个菜单。系统消息（如果有）不加，由实现者判断哪些算系统消息。
- **菜单项**（四项，按此顺序）：
  1. **复制**：复制整条消息的文字，代码卡片复制代码本身，写进剪贴板。
  2. **选择文本**：对这条消息的正文调用第 3 部分的接口（全选，显示手柄和编辑菜单）。
  3. **引用**：把这条消息的引用放进输入框（新的小功能）。形式按微信：输入框上方出现一条"引用：发送者：内容摘要"的条，可以点 × 取消；发送时消息带上引用，消息气泡里显示被引用的内容。具体样式由实现者参照现有气泡决定。
  4. **删除**：从本地会话里删除这条消息（新的小功能）。**我的决定**：不弹确认框，和微信一样直接删除；不涉及服务器（应用目前没有真正的后端同步）。
- 消息正文保持 `.selectable()`。因为气泡有了右键菜单，触摸长按会出应用菜单而不是直接选词，符合"绝不能出现的情况"里的第二条。
- 输入框不用改，自动获得新行为。

## 怎么验证

- **core 无头测试**（Harness，模拟触摸输入）：
  - 长按可选文本时选中一个词；有应用菜单的元素上长按，交给应用。
  - 拖动手柄改变选区，越过时起止交换；拖到边缘时自动滚动。
  - 不在选择状态时，在文字上拖动是滚动。
  - 编辑菜单的菜单项随情况变化（只读、输入框、空选区、剪贴板为空、密码框）。
  - 剪切、复制、粘贴、全选的结果正确（用 `MemoryClipboard`），粘贴后输入法状态推送了新文本和选区。
  - 程序化进入选择。
  - 鼠标输入下，以上行为全部不出现。
- **截图对比**：两种平台风格的手柄、放大镜和菜单各一张，raster 和 vello 各跑一遍。
- **剪贴板**：
  - Android：在一加 6 上从别的应用复制，在 wechat-ui 里粘贴；在 wechat-ui 里复制，在别的应用里粘贴。
  - iOS 模拟器：同样的双向测试（模拟器的剪贴板和 Mac 同步，可以从 Mac 侧确认）。
- **设备手测**：一加 6 和 iOS 模拟器上，按"目标"一节逐条走一遍，包括 Gboard 和 iOS 拼音输入法下的剪切与粘贴。

## 交付顺序（建议）

1. 剪贴板（两个平台）：独立、风险低，做完立刻有用（现有的 Cmd+C 路径和程序化复制在手机上就能用了）。
2. 触摸选择交互和程序化接口（core，主要靠无头测试）。
3. 手柄、菜单、放大镜的绘制和平台风格。
4. wechat-ui 接入和设备验证。

- 按平台适配外观（Material 和 Cupertino），参照 Flutter 的做法，不调用系统原生菜单。
- 触摸下在输入框里直接拖动不再选择文字，改用手柄。
