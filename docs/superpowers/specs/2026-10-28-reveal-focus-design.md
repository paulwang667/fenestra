# 获得焦点的元素滚进可见区域 设计

## 为什么做

fenestra 从不把获得焦点的元素滚进视野：

- 桌面上 Tab 到滚动容器里视野外的输入框或按钮，焦点到了但看不见。
- Android 上键盘弹出时，应用的 Java 层按键盘高度缩小窗口（`onApplyWindowInsets` 加 padding）。原本可见、靠近底部的输入框在窗口变矮后，可能落到滚动容器的可见区域之外，用户看不到自己在输入什么。

用户在 2026-10-28 让我按清单继续（"继续"），流程由我自行推进。

## 目标

1. 焦点移到一个元素（任何途径：Tab、下一项、点击、代码设置、方向键在列表里移动）时，把它所在的各级滚动容器滚动到**刚好**能看到它，外加一点边距。
2. 有焦点时窗口尺寸变化（Android 键盘弹出/收起），同样把焦点元素滚进视野。
3. 已经完整可见时什么都不动。

## 不做什么

- **跟随输入光标**：多行文本框里光标移出视野时自动滚动，不在本次范围（只保证整个元素，或高于视口时元素顶部，可见）。
- **平滑滚动**：直接跳到位置（和浏览器聚焦时一样）。
- **跨平台安全区 API**：仍靠窗口缩小避让键盘。

## 反目标

- 焦点没变、窗口没变时，用户手动滚走的列表被拉回来。
- 已可见的元素获得焦点时列表跳动。
- 正在惯性滑行或回弹时被"拉回焦点"打断——只在焦点变化或窗口变化那一帧做一次。

## 怎么做（已定的部分）

- `FrameState` 记住上一帧的焦点和窗口尺寸。`build_frame` 布局完成后：若焦点变成了另一个元素，或有焦点且窗口尺寸变了，就对焦点元素做一次"滚进视野"。
- 只在那一帧做一次；之后用户随意滚动。
- **算法**（从最内层滚动容器向外）：
  - 目标矩形 = 焦点元素的矩形外扩 8 逻辑像素（`REVEAL_MARGIN`）。
  - 每个滚动祖先的可见区域 = 它的内容框（矩形减去内边距，所以浮动玻璃栏留出的内边距算"不可见"）。
  - 每个轴：目标在可见区域下方/右侧 → 偏移增加差值；在上方/左侧 → 偏移减少差值；目标比可见区域大 → 对齐起始边（顶部/左侧）。
  - 内层滚动后，目标对外层而言换算为"内层可见区域里的那部分"，再对外层做同样的事。
  - 新偏移用 `scroll_to` / `scroll_to_x` 设置（会顺带结束触摸惯性和越界）；下一帧生效，这一帧把 `animating` 置真以确保有下一帧。
- 焦点元素在浮层（菜单、弹出框）里时，同样处理它在浮层内的滚动容器。

## 怎么验证

- core 测试：
  - Tab 到视野外的输入框 → 滚动后它完整可见；
  - 窗口变矮（输入框靠近底部且有焦点）→ 滚动后可见；
  - 已可见的元素获得焦点 → 偏移不变；
  - 嵌套滚动容器 → 内外都滚到可见；
  - 元素高于视口 → 顶部对齐；
  - 焦点不变时用户滚走 → 下一帧不拉回；
  - 内容框内边距（模拟浮动栏）→ 元素不藏在内边距下。
- 真机（一加 6）：临时探针页里，长列表底部的输入框获焦、键盘弹出后仍在可见区域；截图存笔记目录。

## 我替用户做的决定

- 任何途径的焦点变化都触发（包括点击、方向键），和浏览器一致。
- 边距 8 逻辑像素；高于视口时对齐顶部。
- 不跟随光标。
