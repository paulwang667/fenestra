# 光栅化后端的 GPU 毛玻璃：设计

日期：2026-10-27
仓库：fenestra（`/Users/xxxx/projects/fenestra`，推送到 fork `paulwang667/fenestra` 的 `main`）。试验应用：wechat-ui（`/Users/xxxx/projects/wechat-ui/native`）。

## 目的
毛玻璃（`PassKind::BackdropBlur`）现在走"两遍渲染"：先画背景帧，把玻璃周围一块从 GPU **读回 CPU**，在 CPU 上做模糊、饱和度和圆角折射，再把结果当图片塞回第二遍绘制。在一加 6（骁龙 845，Android 9，光栅化后端）上，wechat-ui 的通话卡片显示时每帧 68～105ms：读回 40～60ms，CPU 滤镜 3～35ms。玻璃一出现就远超 16.7ms 的帧预算。

这次把光栅化后端里的毛玻璃**整个搬到 GPU 上**：背景帧本来就在 GPU 纹理里，直接在 GPU 上完成模糊、饱和度、折射，最终绘制直接采样结果纹理，**全程不读回**。做完以后，再在 wechat-ui 上试大面积玻璃（背景铺壁纸或渐变，侧栏、列表、顶栏做成玻璃板），看效果和性能。

## 目标
- 光栅化后端里，所有 `BackdropBlur` 都在 GPU 上完成，一帧里没有任何同步读回（`device.poll` 等待、`map_async` 后阻塞）。
- 外观和现在的 CPU 版本基本一致，具体要保留：
  - 在**线性颜色空间**里模糊（sRGB → 线性 → 模糊 → 饱和度 → sRGB）；
  - 模糊程度：三遍方框模糊近似高斯，`std_dev`（物理像素）的含义不变；大半径时先降采样（规则同现在：系数为 2 的幂，最大 4，降采样后的方框半径不小于 4），再按 `σ²/f² − ¼` 解出低分辨率半径；
  - 读取范围：模糊的输入要包括玻璃周围 `3r` 的边距（"模糊玻璃周围的内容，而不只是正下方"）；
  - 饱和度（`saturation`，即 `backdrop_saturate`）在线性空间按 Rec.709 亮度做；
  - 圆角边缘的折射（`refract_edges`：边缘带宽 `EDGE = 7.0` 逻辑像素乘缩放、按圆角矩形 SDF 的内法线方向往里采样、带少量色散），条件和现在一样：只有玻璃完整在画面内时才做；
  - 输出前加抖动，避免渐变色带（同现在的 `dither`）。
- 玻璃本体（底色、高光 `sheen`、自适应底色、抖动）的合成也在 GPU 上完成。现在它在 `paint_final_into` 里由 `bake_cached` / `glass::bake_body` 在 CPU 上逐像素做（用 f32 合成，最后一次量化加抖动，避免 8 位色带）；GPU 上要保持同样的效果，不能退化成让光栅化后端按普通矢量填充去画底色和高光。
- 自适应底色（`adaptive_tint`，按玻璃后面的平均亮度调整底色明暗）继续可用，而且在**同一帧**生效。wechat-ui 的玻璃（菜单、通话卡片）和 fenestra-kit 的浮层都在用它。
- 两处都走新路径：窗口（`present_raster_frame`）和无头渲染（`Headless` 用光栅化后端时的 `render_plan_raster`）。
- 性能（一加 6，光栅化后端）：
  - 通话卡片或长按菜单显示时滚动消息流，帧间隔稳定在约 16.7ms（p50），不再出现读回；
  - 一块**整屏大小**的玻璃，GPU 模糊本身（降采样、模糊、折射）每帧不超过约 4ms，为大面积玻璃留出余地。
- wechat-ui 上做一次大面积玻璃的试验（见"试验"一节），记录效果截图和帧时间。

## 非目标
- 不改 vello 后端（桌面默认）。它继续走现在的读回加 CPU 路径；试过效果后再决定要不要跟进。
- 不改元素自身的滤镜（`PassKind::ElementFilter`）和自定义 GPU 渲染（`PassKind::Custom`），它们仍走现在的两遍路径。一帧里同时有玻璃和这两种时，只有这两种需要读回，玻璃不需要。
- 不支持 wasm32：网页上的光栅化路径继续画不带模糊的玻璃（现有的 `#[cfg(target_arch = "wasm32")]` 分支），只要求能编译。
- 不追求和 CPU 版本**逐位**一致。CPU 版本的"跨平台逐位确定"是为 vello 截图基准服务的，这里只要求在截图对比容差内一致。
- 不做系统级窗口模糊（macOS vibrancy、Windows Mica/Acrylic），那是另一个功能。
- 不做新的玻璃视觉效果（更强的折射、高光、动态光斑等）；这次只是把现有效果换到 GPU 上。

## 反目标（技术上能跑，但算失败的情况）
- 换成 GPU 以后玻璃看起来明显不同：更糊或更清楚、颜色偏了、圆角处没有折射、边缘出现硬切或色带。
- 仍然有同步读回，只是挪了位置（比如为了自适应底色每帧阻塞读回一个像素）。
- 玻璃内容比背景晚一帧或错位（滚动时玻璃里的模糊画面跟不上下面的内容）。
- 没有玻璃的帧变慢，或者 vello 后端、桌面行为有任何变化。
- 每块玻璃每帧都重新分配纹理，导致内存抖动或卡顿。

## 约束
- 光栅化后端在 `fenestra-raster`（wgpu 渲染管线，不用计算着色器；Android 上要能在 Vulkan 上跑，GL 适配器会自动退回 vello）。新的 GPU 处理也只用普通渲染管线（全屏三角形加片元着色器），不用 compute shader。
- 整个工作区禁止 `unsafe` 代码。
- 现有的两遍结构：`Frame::paint_backdrop_into(target, …) -> specs`，然后 `Frame::paint_final_into(target, …, injected: &HashMap<WidgetId, peniko::ImageData>)`。对玻璃，`paint_final_into` 先用注入图片的像素算自适应底色（`frame.rs` 的 `adapt_fill`：sRGB 字节上的 Rec.709 亮度、每隔 4 个像素采样，再在 OKLCH 里平移底色亮度），再用 `bake_cached` → `glass::bake_body` 在 CPU 上把底色和高光合成进图片，最后把合成好的图片按圆角裁剪画出（`painter::draw_image`），盒子的其余部分（阴影、边框、边缘高光）照常画。光栅化后端对图片按 `ImageData` 的内容标识缓存 GPU 纹理（`fenestra-raster/src/images.rs`）。
- fenestra-core 可以改，但只能**增加**公开接口，不能改已有接口的签名或行为；vello 后端走的代码路径（包括 `paint_final_into` 现有的 CPU 合成）结果不变。
- 窗口路径：`present_raster_frame` 先 `raster_render` 背景帧到光栅化目标纹理，再 `raster_read` 读回区域、`process_specs_in` 做 CPU 处理，最后再 `raster_render` 最终帧。无头路径 `render_plan_raster` 结构相同。
- 必须在 wasm32、Android、iOS 上都能编译（CI 的 `check-targets`）；所有测试按包运行，不跑 `cargo test --workspace`。
- 现有测试全部保持通过；光栅化后端的玻璃截图（在 `FENESTRA_RENDERER=raster` 下）和 CPU 版本的对比在容差内。

## 已经决定的做法
- **GPU 上做完整块玻璃本体**：模糊、饱和度、折射之后，在同一条 GPU 流程里接着合成底色、高光和自适应底色，再量化加抖动，得到最终的玻璃本体纹理——也就是 CPU 路径里 `bake_body` 的输出。合成用到的参数（玻璃的矩形、底色、`sheen`、`adaptive_tint`）由 fenestra-core 新增的公开接口提供给后端（具体形状留给实现者，例如在 `MultiPassSpec` 上加字段，或在 `Frame` 上加一个按 `WidgetId` 查询玻璃本体参数的方法）。
- **已合成的结果通过"占位图片"注入**：光栅化渲染器用一个占位的 `peniko::ImageData`（唯一的内容标识，宽高等于玻璃本体的物理像素尺寸）登记到它的图片缓存里，指向这张纹理。fenestra-core 新增一个入口（例如 `paint_final_into` 的一个变体，或一个告诉它"这些玻璃已经合成好了"的参数），对这些玻璃**跳过** CPU 上的 `adapt_fill` 和 `bake_cached`，直接按圆角画占位图片，并像现在一样去掉盒子样式里已经合成进去的底色、高光和自适应底色。占位图片的像素数据既不会被读取，也不会被上传。vello 后端继续调用原来的 `paint_final_into`，行为不变。
- **结果纹理按玻璃复用**：每块玻璃（按 `WidgetId`）保留它的中间纹理和结果纹理，尺寸不变就不重建；玻璃消失后按现有图层池的方式回收。
- **自适应底色在 GPU 上、同一帧完成**：在 GPU 上对模糊结果求平均亮度（公式与 `adapt_fill` 一致：sRGB 上的 Rec.709 亮度；可以对全部像素求平均，不必照搬"每隔 4 个像素"），在合成着色器里按 `adapt_fill` 的规则在 OKLCH 里平移底色亮度。全程没有读回，也没有一帧延迟。
- **范围**：只在光栅化后端（窗口和无头，非 wasm）启用；vello 后端不变。
- **玻璃部分在画面外时，按正确的方式画**：GPU 路径按玻璃的完整尺寸生成本体，画面外的部分按边缘像素延伸（clamp），不折射。CPU 路径现在会把可见的那一截拉伸到整个玻璃（一个已知的小毛病），GPU 路径不照搬，所以这种情况不和 CPU 比。
- **试验在 wechat-ui 上做**：见下一节。

## 留给实现者决定
- GPU 处理的具体分解：降采样、横竖两个方向的模糊、饱和度和 sRGB 转换、上采样加抖动、折射，各自是一遍还是合并成更少的遍数，只要外观在容差内一致即可。
- 中间纹理的格式（例如线性空间用 `Rgba16Float`，或在 `Rgba8Unorm` 上自己做 sRGB 转换），注意 Android Vulkan 上的格式支持。
- 读取背景帧：直接采样 MSAA resolve 之后的光栅化目标纹理，还是先拷一份到独立纹理（光栅化目标纹理在最终帧里会被重新渲染，注意读写冲突）。
- 占位图片和 GPU 纹理在图片缓存里怎么登记、何时失效。
- 自适应底色的平均亮度怎么在 GPU 上算（逐级降采样，或一遍求和），以及异步读回的缓冲怎么复用。
- 玻璃截图对比的容差取值（参照光栅化后端已有的 EDGES/FILLS/TEXT 预算）。

## 验收
- 新测试：GPU 路径产生的玻璃本体和 CPU 版本（`blur_linear_crop` + `refract_edges` + `bake_body` + `adapt_fill`）在容差内一致，至少覆盖：小半径不降采样、大半径降采样、带饱和度、带圆角折射、带底色和高光、带自适应底色（在深色和浅色背景上各一次）；玻璃部分在画面外时内容不被拉伸、不折射；一帧里没有同步读回（通过渲染器的统计计数断言，例如"读回次数为 0"）。
- fenestra 原有测试、clippy（桌面和 Android）、wasm 和 iOS 编译检查全部通过；推送后 CI 全绿。
- 一加 6 实测：wechat-ui 通话卡片显示时滚动、长按菜单打开时的帧时间；大面积玻璃试验的截图和帧时间，记进笔记目录的 `FRAME-TIME-31MS.md`。
